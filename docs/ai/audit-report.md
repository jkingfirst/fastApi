## 关键问题证据、影响与验证

### P1-01 未鉴权删除

`delete_user` 只依赖 `get_session`，没有 Bearer token、当前用户或角色依赖，随后以请求的 `userId` 执行 SQL delete。任意可访问该 API 的调用方均可提交 ID。建议先确认删除权限模型，再增加认证、资源归属/角色校验和不存在资源的 404 响应。修复会使既有匿名调用收到 401/403，属于 API 兼容性变更。验证应覆盖匿名、普通用户、管理员、本人/他人、缺失用户和关联数据。

### P1-02 HTTP 异常路径

`getattr(exc, 'code', ErrorCode.UNKNOWN)` 中的默认表达式会先被求值，但 `ErrorCode` 没有 `UNKNOWN` 成员。建议改为已定义的映射规则，并以 404、405、登录失败和无效 token 的请求测试固定响应。实际 HTTP 结果尚未运行验证，但该 Python 表达式错误可由代码确认。

### P1-03 可复现依赖

源码使用 `jwt`、`pwdlib` 和 `OAuth2PasswordRequestForm` 所需的 multipart 支持，`requirements.txt` 未声明相应直接依赖。质量基线中 `pip check` 退出码为 0，只说明当前已安装包元数据无冲突，不能证明干净环境可安装运行。建议获批后在新虚拟环境验证安装和表单登录。

### P1-04 用户唯一性

`email` 唯一，`username` 不唯一；登录以用户名查询并使用 `scalar_one_or_none()`。两个不同邮箱使用同一用户名即可触发多行查询异常。应先确认登录标识，再制定重复数据清理和唯一索引迁移方案；不得直接在有存量数据的库上新增约束。验证需包括并发和重复注册。

### P1-05 密钥与配置

JWT 签名密钥在受版本控制源码中定义，数据库 URI 在本地配置文件中直接定义。本文不记录敏感值。建议使用环境变量或受管密钥系统，并轮换已暴露的凭据；JWT 轮换会使历史 token 失效，需提前制定兼容策略。

### P1-06 迁移风险

密码迁移新增非空哈希列后删除旧列，未见数据转换、重置或备份逻辑。当前数据库版本和存量数据未知，因此这是待确认风险而非已验证的数据损坏。应在匿名化副本演练升级、登录和降级，再决定修复方案。
